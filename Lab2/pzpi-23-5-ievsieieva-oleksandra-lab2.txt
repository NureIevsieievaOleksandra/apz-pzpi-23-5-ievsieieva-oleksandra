2 ЗАВДАННЯ

	На цій лабораторній роботі потрібно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ, вказані лектором, а саме Kotlin для Android та Swift для iOS.
	Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи. 
3 ОПИС ВИКОНАНОЇ РОБОТИ

	Для реалізації мобільного клієнта обрано платформу Android та мову програмування Kotlin. Архітектура застосунку побудована на принципах Clean 	Architecture з використанням шаблону MVVM (Model-View-ViewModel), що забезпечує чіткий розподіл відповідальності.
	Ключові технології:
•	Room Persistence Library: для локального кешування даних та підтримки роботи в офлайн-режимі.
•	Ktor Client: для здійснення HTTP-запитів до сервера (REST API) та підтримки протоколу WebSockets для оновлення стану в реальному часі.
•	Coroutines & Flow: для асинхронної обробки даних та реактивного оновлення інтерфейсу користувача.
•	Koin: для впровадження залежностей (Dependency Injection).
	Застосунок розділений на логічні шари:
•	Presentation Layer: ViewModel взаємодіє з UI через StateFlow, забезпечуючи відображення списків кімнат (груп) та ламп.
•	Domain/Repository Layer: Шар репозиторіїв (наприклад, GroupRepository) виступає єдиним джерелом істини. Він вирішує, чи брати дані з локальної БД, чи оновлювати їх через мережу.
•	Data Layer: Включає опис сутностей БД (Entity), об'єктів передачі даних (DTO) та логіку мережевих викликів з обробкою помилок (safeCall).
	На рисунку 1 наведено діаграму Use case.
 
Рисунок 1 – Діаграма Use case

	Для візуалізації того, як компоненти застосунку взаємодіють між собою, нижче наведено діаграму компонентів. Вона демонструє зв’язки між репозиторіями, локальною базою даних та зовнішнім API (див. рис. 2).

 
Рисунок 2 – Діаграма компонентів

	Застосунок взаємодіє з сервером Ktor через REST API для виконання операцій створення/редагування/видалення груп та ламп. Після отримання відповіді від сервера дані автоматично синхронізуються з локальною базою даних Room.
	Нижче наведено приклад реалізації логіки безпечного виклику API та збереження даних у локальну БД:
01 suspend inline fun <reified T> safeCall(
02     execute: () -> HttpResponse
03 ): Result<T, DataError> {
04     val response = try {
05         execute()
06     } catch(e: SocketTimeoutException) {
07         return Result.Error(DataError.Remote.REQUEST_TIMEOUT)
08     } catch(e: UnresolvedAddressException) {
09         return Result.Error(DataError.Remote.NO_INTERNET)
10     } catch (e: Exception) {
11         return Result.Error(DataError.Remote.UNKNOWN)
12     }
13     return responseToResult(response)
14 }
15
16 override suspend fun load(): Unit = withContext(Dispatchers.IO) {
17     safeCall<List<GroupDto>> {
18         httpClient.get("group")
19     }.onSuccess { list ->
20         dbRepository.db.groupDao.insert(list.map { it.toEntity() })
21         dbRepository.db.lampDao.insert(list.flatMap { it.lamps }.map { it.toEntit() })
22     }
23 }

	Як видно з діаграми, центральним елементом є репозиторій, який агрегує дані з різних джерел. Нижче наведено приклад опису структури бази даних, а саме сутності «Група» (кімната), яка містить список ламп через відношення @Relation.
01 @Entity
02 data class GroupEntity(
03     @PrimaryKey val groupId: Long,
04     val name: String? = null,
05     val description: String? = null,
06 )
07 
08 data class Group(
09     @Embedded val group: GroupEntity,
10     @Relation(
11         entity = LampEntity::class,
12         entityColumn = "groupId",
13         parentColumn = "groupId",
14     ) val lamps: List<LampEntity>
15 )

	Процес взаємодії користувача із застосунком можна представити у вигляді діаграми активності (Activity Diagram). Вона описує шлях від запуску програми до отримання актуальних даних про стан ламп у кожній кімнаті (див. рис. 3).
	Одним із найважливіших аспектів взаємодії є стабільність. Оскільки мобільні мережі можуть бути нестабільними, реалізовано механізм safeCall. Він перехоплює виключення (наприклад відсутність інтернету) і повертає типізовану помилку замість аварійного завершення програми.
	Приклад реалізації синхронізації даних (завантаження груп з сервера та збереження їх у локальну БД):
