2 ЗАВДАННЯ

	В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: - масштабувати сервер горизонтально – багато копій сервера виконують однакові функції для різних користувачів; - масштабувати сервер вертикально – різні мікросервіси виконують різні функції і масштабуються окремо одне від одного.
	З технічної точки зору, масштабування можна виконати так: - деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; - деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне).Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. - ваш власний спосіб показати що система може масштабуватись. 
	На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система.. 
3 ОПИС ВИКОНАНОЇ РОБОТИ

	Для демонстрації можливостей горизонтального масштабування серверної частини розподіленої системи було обрано архітектурний підхід із розгортанням контейнеризованого застосунку в локальному кластері Kubernetes, активованому через середовище Docker Desktop. На першому етапі розробки інфраструктури було створено маніфест розгортання, який описує параметри функціонування бекенд-вузлів на базі фреймворку Ktor. У цьому конфігураційному файлі було чітко визначено простір імен для ізоляції ресурсів, а також задано початкову кількість реплік, що дорівнює двом одиницям. Це дозволяє системі забезпечити базову відмовостійкість та розподіл трафіку між декількома екземплярами застосунку з перших секунд запуску. Контейнер налаштований на постійне оновлення образу при перезапуску та отримує параметри підключення до бази даних PostgreSQL через змінні оточення, зокрема використовуючи безпечний механізм посилань на секрети кластера для передачі конфіденційних даних користувача та пароля.
	Нижче наведено фрагмент конфігураційного маніфесту deployment.yaml, який відповідає за створення подів застосунку та визначення політики їх масштабування.
1 apiVersion: apps/v1
2 kind: Deployment
3 metadata:
4   name: ktor-app
5   namespace: smartlight
6 spec:
7   replicas: 2
8   selector:
9     matchLabels:
10      app: ktor-app

	Після опису логіки розгортання серверних контейнерів виникла необхідність організації єдиної точки входу для обробки користувацьких запитів та автоматичного балансування навантаження між створеними подами. Для вирішення цього завдання було спроектовано та застосовано маніфест сервісу типу LoadBalancer, який функціонує в тому самому просторі імен кластера. Цей сервіс здійснює відстеження активних екземплярів бекенду за допомогою селектора міток і перенаправляє зовнішній трафік з порту вісімдесят-вісімдесят на аналогічний цільовий порт контейнера. Завдяки такій конфігурації забезпечується прозора інтеграція з локальним балансувальником Docker Desktop, що дозволяє проводити подальше тестування системи у стійкому та наближеному до реального виробничого середовища режимі.
	Опис мережевого сервісу балансування навантаження представлено у наступному фрагменті файлу service.yaml.
1 apiVersion: v1
2 kind: Service
3 metadata:
4   name: ktor-service
5   namespace: smartlight
6 spec:
7   type: LoadBalancer
8   selector:
9     app: ktor-app

	Наступним кроком для виконання умов отримання максимальної оцінки стало проектування сценарію навантажувального тестування за допомогою інструменту Locust. Створений тестовий скрипт описує поведінку віртуального користувача інтелектуальної системи освітлення, який з певною імітаційною затримкою виконує типові операції на сервері. У логіці роботи скрипта передбачено обов'язкову процедуру авторизації при старті сесії, під час якої генерується POST-запит до відповідного ендпоінту з передачею облікових даних, після чого отриманий токен безпеки зберігається та динамічно підставляється в заголовки всіх наступних запитів для автентифікації.
	Структура ініціалізації користувача та формування авторизаційних заголовків у файлі locustfile.py виглядає наступним чином.
1 class SmartLightUser(HttpUser):
2     wait_time = between(1, 3)
3     token = None
4     def on_start(self):
5           response = self.client.post("/signIn", json={"username": "admin", "password": "Secret1"})
6           if response.status_code == 200:
7               self.token = response.json().get("token")
8     def auth_headers(self):
9         return {"Authorization": f"Bearer {self.token}", "Content-Type": "application/json"}

	Для створення реалістичного профілю навантаження в тестовому сценарії було реалізовано три основні завдання з різними ваговими коефіцієнтами частоти виклику. Найбільшу вагу отримала задача надсилання запитів на отримання списку груп освітлення, що відображає типову поведінку користувачів, які найчастіше просто переглядають поточний стан системи. Меншу вагу встановлено для завдання генерації аналітики, а найрідше виконується операція модифікації параметрів конкретної лампи, яка супроводжується випадковою генерацією колірних каналів та рівнів яскравості. Такий розподіл дозволяє комплексно перевірити як операції читання з бази даних, так і операції запису під час паралельної роботи великої кількості користувачів.
	Розподіл навантажувальних завдань із різною пріоритетністю у locustfile.py реалізовано через відповідні декоратори.
1     @task(3)
2     def get_groups(self):
3         self.client.get("/group", headers=self.auth_headers(), name="GET /group")
4     @task(1)
5     def update_lamp(self):
6         self.client.put("/lamp", headers=self.auth_headers(), json={
7             "lampId": 30, "r": random.randint(0, 255), "brightness": random.randint(0, 100)
8         }, name="PUT /lamp")

	Фінальний етап лабораторної роботи полягав безпосередньо у проведенні експерименту з горизонтальним масштабуванням для фіксації змін у пропускній здатності системи. Спочатку тестування було запущено для конфігурації з двома активними подами, під час якого фіксувалися показники кількості успішних запитів на секунду та середній час відповіді сервера. Після цього за допомогою стандартних команд керування кластером Kubernetes було проведено динамічне збільшення кількості реплік застосунку Ktor, що призвело до автоматичного підключення нових подів до балансувальника сервісу. Повторне зняття метрик у Locust продемонструвало лінійне зростання загальної кількості оброблюваних системою запитів на секунду та зниження затримок, що повністю підтверджує ефективність горизонтального масштабування розробленого бекенду при роботі з інтенсивним навантаженням.
 
4 ВИСНОВКИ

	У ході виконання лабораторної роботи було практично досліджено механізми горизонтального масштабування серверної частини розподіленої системи в середовищі Kubernetes з використанням інструментів контейнеризації Docker Desktop. Розгортання декількох реплік застосунку та налаштування мережевого сервісу типу LoadBalancer дозволило забезпечити ефективний розподіл вхідного трафіку між подами, гарантуючи високу відмовостійкість та стабільність системи. Проведене навантажувальне тестування за допомогою інструменту Locust наочно продемонструвало, що динамічне збільшення кількості активних інстансів бекенду забезпечує лінійне зростання пропускної здатності системи, виражене у збільшенні кількості успішно оброблених запитів на секунду. Таким чином, обраний архітектурний підхід повністю підтвердив свою ефективність для оптимізації вебзастосунків під час роботи в умовах критично високих навантажень..
