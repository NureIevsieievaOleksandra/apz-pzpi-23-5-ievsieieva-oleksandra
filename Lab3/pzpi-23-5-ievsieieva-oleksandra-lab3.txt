2 ЗАВДАННЯ

	На цій лабораторній роботі потрібно розробити front-end частину програмної системи. Ця частина системи повинна підтримувати роботу клієнтів у веб-режимі та забезпечувати адміністрування системи, тобто мати окремий інтерфейс для звичайних користувачів і окремий — для адміністраторів (відповідно до ролей користувачів вашої системи).
	Користувацький інтерфейс та інтерфейс адміністрування повинні підтримувати інтернаціоналізацію та локалізацію, а саме, забезпечувати: підтримку української на англійської мов сайту, формат дати та часу відповідний регіону, порядок сортування текстових значень, різні напрями введення тексту тощо.
	Адміністрування системи повинно забезпечувати: управління користувачами системи, управління даними системи, створення резервних копій налаштувань та даних, експорт та імпорт даних та налаштувань.системи. 
3 ОПИС ВИКОНАНОЇ РОБОТИ

	При проектуванні фронтенд-частини системи "Smart Light Admin" було обрано стек технологій Kotlin Multiplatform та Jetpack Compose. Це дозволяє забезпечити єдину бізнес-логіку для різних платформ, зберігаючи при цьому нативну продуктивність інтерфейсу.
	Для забезпечення стабільності стану інтерфейсу використано реактивний підхід. Кожен екран (наприклад, DashboardScreen) керується своєю ViewModel, яка оперує трьома складовими:
•	State: єдине джерело істини для UI (наприклад, список користувачів, стан завантаження).
•	Action: наміри користувача (натискання кнопок, введення тексту).
•	Event: одноразові події (навігація, показ повідомлень).
	Для керування життєвим циклом об'єктів використано бібліотеку Koin. Система розділена на модулі для забезпечення слабкої пов'язаності компонентів (Loose Coupling):
•	appModule: реєстрація ViewModel.
•	repositoryModule: зв'язування інтерфейсів репозиторіїв з їх реалізаціями.
•	networkModule: конфігурація HTTP-клієнта.

2      singleOf(::AuthRepositoryImpl).bind<AuthRepository>()
3      singleOf(::UserRepositoryImpl).bind<UserRepository>()
4      singleOf(::AdminRepositoryImpl).bind<AdminRepository>()

	Взаємодія між UI-шаром та віддаленим сервером побудована на принципі безпечних викликів. Використовується механізм safeCall, який інкапсулює обробку виключень та перетворення HTTP-відповідей у зрозумілі для бізнес-логіки типи.
	Система розрізняє технічні помилки (відсутність інтернету, таймаут) та помилки бізнес-логіки (API Error). Для цього реалізовано ієрархію DataError.
1  suspend inline fun <reified T> safeCall(
2      execute: () -> HttpResponse
3  ): Result<T, DataError> {
4      return try {
5          val response = execute()
6          responseToResult(response)
7      } catch(e: UnresolvedAddressException) {
8          Result.Error(DataError.Remote.NO_INTERNET)
9      }
10 }

Рисунок 3 – UML діаграма взаємодії

	Діаграма діяльності ілюструє потік подій при виконанні адміністративної операції: 
•	Дія користувача: Адміністратор натискає іконку додавання на сторінці AdminPage, що генерує подію Dashboard.Action.OnCreateBackup.
•	Обробка у ViewModel: Метод onAction перехоплює подію та викликає приватну функцію createBackup().
•	Виклик Репозиторію: AdminRepository ініціює POST-запит до ендпоінту admin/backup.
•	Рівень мережевої безпеки (SafeCall):
•	Виконується запуск корутини у контексті Dispatchers.Default.
•	Блок safeCall огортає мережевий виклик httpClient.post для перехоплення виключень, таких як NoInternet або SocketTimeout.
•	Розгалуження результату (Decision Node):
•	Success: Якщо сервер повертає статус 200–299, викликається loadBackups() для отримання оновленого списку файлів, і стан State.backups оновлюється.
•	Error: Якщо виникає помилка (наприклад, 500 Server Error), вона трансформується у DataError, і повідомлення виводиться в консоль (або лог) через toErrorMessage().
•	Завершення: Система повертається в стан очікування дій користувача, відображаючи актуальний список або помилку.
